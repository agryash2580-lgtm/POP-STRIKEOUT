# Strikeout: risk ranking and AI hallucination controls

## The explanation to give the judges

“We implemented two controls. First, findings from different sources are ranked by potential severity, with evidence strength breaking ties. Second, AI output is checked on the server: guidance must match a supplied source passage, observations must match selected evidence notes, and unsupported output is rejected. Pop uses AI to select reviewed guidance rather than invent unrestricted answers.”

## 1. Ranking retrieved information

### What the requirement means

The app retrieves information from multiple sources. Users should see the findings that could cause the greatest harm first.

This implementation ranks results **after retrieval**. It does not change which provider is queried first or make retrieval faster.

### What defines severity?

These are explicit rules written in code, not severity guesses generated by Gemini.

| Severity | Findings | Potential impact |
|---|---|---|
| Critical | Credential-like assignments; breach records containing credential-related data classes | Possible account access or takeover |
| High | Possible identity documents; checksum-valid payment-card patterns; breach records with financial or identity data classes | Possible impersonation or financial misuse |
| Medium | Email/phone references; other breach memberships | Possible phishing, scams or unwanted contact |
| Low | Social or professional profile references alone | Limited evidence of sensitive exposure |

Unknown categories receive **provisional medium severity** and a manual-review explanation.

A pattern is not confirmation. A card checksum does not prove a real card exists. A breach record does not prove a password still works. A possible identity-document match does not verify ownership.

### What defines evidence strength?

Within the same severity, findings are ordered by these fixed weights:

| Evidence | Weight |
|---|---:|
| Breach-provider record | 3 |
| Exact identifier occurrence in checked text | 2 |
| Formatted phone-number or profile-path match | 1 |
| Unverified search lead, pattern or unknown confidence | 0 |

The weights are ordering rules, **not percentages or calibrated probabilities**. Equal severity and evidence preserve the original result order.

Example: a possible exposed credential ranks above a confirmed ordinary email reference. Its potential impact is greater, even though the credential pattern still needs verification.

External results are ranked before the existing URL/name deduplication, so that the higher-ranked duplicate survives. Supplied-document findings are also ranked. Each finding displays its severity and the reason for its position.

### Where it lives

- `api/osint/prioritize.mjs`: severity rules and evidence ordering.
- `api/osint/osint.mjs`: applies ranking to external findings before deduplication.
- `api/osint/documents.mjs`: applies ranking to supplied-document findings.
- `frontend/src/app/components/ExposureApp.tsx`: displays severity and reasons.
- `tests/retrieval-priority.test.mjs`: ranking and integration tests.

## 2. Reducing AI hallucinations

### What was wrong before?

The report already checked citation IDs. But an AI could attach a real source ID to a made-up claim.

For example, “Your account has been recovered [S1]” could cite an existing recovery-help source. The source ID exists, but that does not establish that recovery happened.

### What now happens?

| Area | Control |
|---|---|
| Report guidance | Must equal one whole excerpt from a cited source, apart from whitespace |
| Evidence observations | Must equal a whole selected evidence note and reference its correct evidence ID |
| Summary and complaint | Server templates use supplied case fields and label the account user-reported and the complaint unsubmitted |
| Step titles and limitations | Supplied by server-owned product text |
| Research sources | URLs without grounding text cannot support researched guidance |
| Saved-report help | Restricted to allowed saved passages; guidance excludes steps recorded as completed |
| Missing support | Can return an explicit insufficient-evidence response; invalid generated claims produce a rejection rather than being shown |
| Pop chat | AI selects a reviewed response ID; the server supplies the actual response text |

### Why match a whole passage?

Taking only part of a sentence can reverse its meaning.

Source: “Never share recovery codes.”

Bad extraction: “Share recovery codes.”

The whole-passage check rejects that change. It also rejects added sentences such as “Recovery is guaranteed.”

### How Pop works now

1. Gemini receives the deliberately supplied conversation context.
2. It selects an ID such as `recovery`, `evidence`, `reporting` or `unknown`.
3. The server validates the response structure and ID.
4. The server renders the reviewed text for that ID.

Invented IDs, additional generated claims, invalid JSON and truncated responses are rejected. Pop does not gain account access, live search or the ability to perform recovery actions.

**Tradeoff:** Pop is more limited conversationally, and report guidance is extractive rather than freely rewritten. The model can still select an irrelevant response or passage.

### What this does not guarantee

This is hallucination reduction, not a claim of zero hallucinations.

- Search excerpts arrive through Gemini grounding metadata. They are not independently fetched, verified verbatim source documents.
- Bundled references remain labelled as bundled, rather than newly researched.
- Exact matching does not establish that a source is true or current.
- User statements remain user-reported; copying them does not verify them.
- Conflicting sources are not automatically reconciled.
- Attachment consent remains available, but generated observations cannot introduce unsupported interpretations of attachments.
- These tests use synthetic provider responses. Live Gemini and source-quality evaluation remain outstanding.

### Where it lives

- `api/ai-grounding.mjs`: passage checks, abstention text and reviewed Pop responses.
- `api/report-ai.mjs`: report and saved-help validation.
- `api/pop.mjs`: structured response selection and rejection of invalid AI replies.
- `tests/ai-grounding.test.mjs`: eight focused grounding tests.
- `tests/pop-api.test.mjs` and `tests/reports.test.mjs`: updated provider and authenticated integration tests.
- `AI-GROUNDING.md`: implementation tradeoffs and limitations.

## 4. Questions you should be able to answer

**Is risk the same as confidence?** No. Severity describes potential harm; evidence strength describes the basis of the finding. This version orders by severity first and evidence strength second. It does not calculate a statistical risk probability.

**Does a valid citation make a claim true?** No. We also check that the guidance matches a whole passage associated with that citation. Source truth still requires review.

**Why not just prompt Gemini to avoid hallucination?** A prompt is a request. Server validation can reject output that breaks the allowed format or grounding rules.

**Can you claim hallucinations are eliminated?** No. We can demonstrate specific unsupported outputs being rejected, and explain the remaining limits.
